## Plan d'implémentation — U03 Schéma de base et migrations

Validé par le fondateur le 8 octobre 2026.

### Ce que nous construisons

Le schéma Drizzle de toutes les tables de `architecture.md` (Storage Model), généré en migrations SQL versionnées, complétées de migrations SQL personnalisées pour ce que Drizzle ne génère pas (RLS sur toutes les tables, clé étrangère `profiles.id` → `auth.users`, buckets privés, valeurs initiales de `app_settings`). Une pile Supabase locale (CLI, Docker) sert de base de développement et de test. Un script de seed local crée 1 admin et 1 utilisateur. Des tests d'intégration prouvent que la clé publique Supabase ne lit aucune ligne ; ils tournent aussi en CI. Un workflow applique les migrations en préproduction et en production (avec approbation).

### Vocabulaire validé

- **Base vide** : Supabase local fraîchement démarré, seuls les schémas internes (`auth`, `storage`…) existent.
- **Clé publique Supabase** : clé « publishable » (ex-« anon ») ; avec elle, chaque table renvoie zéro ligne même si elle contient des données.
- **Seed local** : script refusant toute base non locale ; 1 admin + 1 utilisateur via l'API d'administration Auth, avec leurs `profiles`.
- **`app_settings` initial** : valeurs d'AD-20 posées par migration (donc aussi en préproduction et production).

### Décisions prises

1. Supabase CLI en local (`supabase start`, Docker), version épinglée appelée par `npx`.
2. Une seule chaîne de migrations, gérée par `drizzle-kit` (générées + personnalisées). Pas de `supabase/migrations`.
3. Workflow `db-migrate.yml` : migrations appliquées au push sur `staging` (préproduction) et sur `main` (production, environnement GitHub protégé avec approbation).
4. Enums PostgreSQL pour les statuts ; `uuid` ; montants entiers (`bigint` pour les cumuls de micro-euros) ; `timestamptz` ; index sur les colonnes filtrées.
5. Client applicatif `src/server/db/client.ts` et `DATABASE_URL` dans `env.ts` reportés à U04 (premier usage).
6. Tests d'intégration `npm run test:db` (tables présentes, RLS partout, clé publique sans accès, buckets privés), job CI dédié qui démarre Supabase.

### Hypothèses

- Les noms de colonnes suivent `architecture.md` ; les détails absents (index, contraintes `check`, valeurs par défaut) sont choisis au plus simple et documentés dans le schéma.
- Les projets Supabase de préproduction et de production sont créés par le fondateur ; leurs URL de base de données deviennent des secrets d'environnement GitHub (`docs/setup-deploiement.md`).

### Comment le construire

1. `supabase init`, `supabase start` ; récupérer URL, clés, URL Postgres locales.
2. Installer `drizzle-orm`, `drizzle-kit`, `postgres`, `@supabase/supabase-js` (versions exactes, lockfile avec le npm de la CI).
3. Écrire le schéma, générer la première migration, ajouter les migrations personnalisées.
4. `db:migrate` sur la base vide ; seed ; tests d'intégration.
5. CI et workflow de migration ; documentation.
6. lint, typecheck, test, test:db, build ; `/review`, `/audit` ; commit et push sur `dev`.

### Vérification

- `supabase db reset` (base vide) puis `npm run db:migrate` : toutes les tables créées, sans erreur ; deuxième exécution sans effet.
- `npm run test:db` : 13 tables présentes, RLS activée sur chacune, aucune ligne lisible avec la clé publique (avec des lignes insérées par le seed), 3 buckets privés, `app_settings` initial conforme à AD-20.
- Même suite verte dans le job CI.

### Invariants concernés

- 13 : migrations jamais modifiées après application ; toute évolution = nouvelle migration.
- Accès base uniquement serveur : RLS sans politique, clé publique sans aucun accès (testé).
- 5 et 6 : `subscriptions`, `billing_events` (idempotence) et `admin_audit_log` créés avec les contraintes d'unicité nécessaires.
- 10 : `consents` avec le type `b2b`.
