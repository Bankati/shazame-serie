## Plan d'implémentation — U10 Cache par empreinte

Validé par le fondateur le 15 octobre 2026 (« ce que tu penses être la meilleure option »).

### Ce que nous construisons

Le cache de résultats côté serveur : à partir des JPEG reçus, le serveur calcule lui-même un dHash 64 bits par image (`sharp`), cherche une entrée identique (empreinte d'extrait, index unique) puis proche (au moins 2 images à ≤ 6 bits, SQL `bit_count`) parmi les entrées non désactivées. Un succès renvoie le résultat avec `source: "cache"` et incrémente `hits` ; sinon la fonction d'identification fournie est appelée et son résultat est écrit en cache seulement si la confiance atteint 80 % (ou s'il est validé). Une entrée peut être désactivée (signalement). Le client de base applicatif (`src/server/db/client.ts`) et `DATABASE_URL` sont créés ici, premier usage.

### Vocabulaire validé

- **Empreinte d'image** : dHash 64 bits calculé par le serveur sur chaque JPEG reçu (invariant 4).
- **Empreinte d'extrait** : SHA-256 des empreintes d'images triées ; identifie un jeu d'images identique.
- **Correspondance proche** : entrée dont au moins `CACHE_MIN_MATCHING_FRAMES` (2) images reçues sont à ≤ `CACHE_MAX_HAMMING` (6) bits d'une de ses images.
- **Entrée utilisable** : entrée non désactivée (`disabled = false`).

### Décisions prises

1. Correspondance exacte et proche dans PostgreSQL (AD-29) : pas de raccourci Redis en V1 (index unique ≈ 1 ms, une dépendance de moins). Redis reste pour quotas et limitation de débit (U11). À revoir au-delà de ~100 000 entrées.
2. `withResultCache(images, onMiss)` : point d'entrée réutilisé par U11, qui placera quota et IA dans `onMiss`.
3. Écriture si confiance ≥ `CACHE_MIN_CONFIDENCE` (80) ou entrée validée ; empreintes d'images dédoublonnées avant insertion (clé primaire `cache_id, frame_hash`).
4. dHash stocké signé (`BigInt.asIntN(64, …)`) car `bigint` PostgreSQL est signé ; la distance de Hamming est identique.
5. Client Drizzle + `postgres` avec `prepare: false` (pooler en mode transaction), créé à la première utilisation ; `DATABASE_URL` obligatoire en production, facultative ailleurs.

### Hypothèses

- `bit_count(bit)` disponible (PostgreSQL 17, local et Supabase).
- Les seuils (6 bits, 2 images, 80 %) sont des valeurs de départ, calibrées en U13.

### Comment le construire

1. Installer `sharp` 0.35.5 ; `DATABASE_URL` dans `env.ts` ; client Drizzle.
2. dHash serveur + empreinte d'extrait + tests unitaires.
3. Cache : recherche, écriture, désactivation, `withResultCache`.
4. Tests d'intégration (images JPEG générées, recompressées, différentes).
5. lint, typecheck, test, test:db, build ; `/review`, `/audit` ; commit et push sur `dev`.

### Vérification (critère de fin)

- Même jeu d'images deux fois → `onMiss` appelé une seule fois, second résultat `source: "cache"`.
- Images recompressées (qualité JPEG plus basse, légère réduction) → toujours un succès.
- Images d'un autre extrait → pas de correspondance.
- Entrée désactivée → plus de succès ; confiance < 80 % → rien d'écrit.

### Invariants concernés

- 4 : empreintes calculées uniquement par le serveur à partir des octets reçus ; aucun paramètre ne permet d'en fournir une.
- RG6 : un succès du cache n'appelle pas `onMiss` (où vivront IA et décompte en U11).
- RG7 : seules les empreintes et le résultat sont stockés, jamais les images.
