# Plan d'implémentation — U34 Identification par image

Validé par le fondateur le 20 octobre 2026 (« je suis d'accord avec toi »). Décisions AD-38 et AD-42.

## Ce que nous construisons

La zone d'envoi accepte, en plus d'une vidéo, 1 à 5 images (JPEG, PNG, WebP, HEIC/HEIF) : captures d'écran ou photos d'un écran. Le navigateur les décode (HEIC par un décodeur chargé seulement si besoin), les réduit à 768 px, écarte les noires, floues et doublons (1 image exploitable suffit), puis envoie le paquet JPEG à `/api/identify` avec `mode=images`. Le serveur applique le même circuit que le clip (type réel, 1,5 Mo, quota, cache par empreinte, décompte RG3, plafond IA), avec une consigne IA propre au mode image, et enregistre le mode dans `identifications.input_kind`. Le signalement accepte 1 à 5 images.

## Vocabulaire validé

- **Identification par image** : 1 à 5 captures ou photos d'écran, pas forcément du même instant ; même circuit que le clip.
- **Capture exploitable** : ni noire, ni floue, ni doublon ; 1 suffit (2 pour un clip).
- **Même capture** : empreinte identique calculée par le serveur → cache, sans décompte (RG6).
- **Mode** (`input_kind`) : `clip`, `images` ; `description` et `link` réservés pour U35-U36.

## Décisions prises

- **Mode en base** : enum `input_kind` (`clip`, `images`, `description`, `link`), colonne `identifications.input_kind` non nulle, `clip` par défaut ; migration `0005` (aucune migration appliquée modifiée, invariant 13).
- **Zone unique qui reconnaît le fichier** (pas d'onglets avant U35) : une vidéo → clip ; 1 à 5 images → mode image ; mélange, plus de 5 images ou plusieurs vidéos → message clair.
- **Même route `/api/identify`**, champ `mode` (zod, `clip` par défaut pour compatibilité) ; minimum 1 image en mode `images`, 2 pour `clip` ; maximum 5, 1,5 Mo, type JPEG réel inchangés.
- **Consigne séparée `identify-images.v1`** ; la consigne du clip (`identify.v1`) ne change pas. Version enregistrée avec l'identification.
- **Cache partagé entre modes** ; correspondance proche toujours à 2 images au moins (une seule capture : correspondance exacte seulement, pas de faux positif sur une image isolée).
- **HEIC** : `heic-to` 1.6.5 (LGPL-3.0, non modifiée, chargée à part et seulement si le navigateur ne décode pas l'image).
- **Taille d'une image reçue** : 30 Mo au plus avant réduction (photos d'appareil).

## Hypothèses

- iOS convertit les photos HEIC en JPEG à la sélection depuis la galerie ; le décodeur HEIC sert surtout sur ordinateur.
- La consigne image n'est pas encore évaluée (`npm run eval` attend U13) : à mesurer dès que le jeu de test existe.

## Comment le construire

1. Base : enum, colonne, migration générée, appliquée en local.
2. Serveur : mode dans le schéma, la validation, le pipeline, l'enregistrement, la consigne (tests d'abord).
3. Navigateur : contrôle et préparation des images, paquet à 1 image minimum, hook, envoi du mode.
4. Interface : sélection multiple, textes, messages.
5. Tests : Vitest (validation, pipeline, cache), base locale (colonne, cache exact à 1 image), Playwright (capture → résultat, refus).

## Vérification

- Vitest : 1 à 5 images en mode image, 2 à 5 en clip ; 1,5 Mo ; `mode` invalide refusé ; consigne image utilisée ; `input_kind` enregistré.
- Base locale : une capture déjà vue sert le cache (correspondance exacte), sans décompte (`counted = false`).
- Playwright : capture → résultat (requête `mode=images`, 1 image) ; 6 images ou vidéo + image → message ; signalement avec une seule capture.

## Invariants concernés

- 1 : jamais de vidéo ; 1 à 5 images JPEG en mode image (AD-38), 1,5 Mo, type réel vérifié par le serveur.
- 2 : la consigne image passe par `server/ai` et la garde de dépense.
- 3 : décompte inchangé (`quota.commit()` après résultat ≥ 50 % issu de l'IA).
- 4 : empreintes calculées par le serveur, aussi pour une seule image.
- 7 : `mode` validé par zod avant toute logique.
- 9 : aucune image ni nom de fichier dans les journaux.
- 13 : nouvelle migration seulement.
