## Plan d'implémentation — U01 Socle du dépôt et déploiement

Validé par le fondateur le 7 octobre 2026.

### Ce que nous construisons

Le squelette Next.js existant devient un socle déployable : versions d'outillage cohérentes, `src/server/env.ts` (validation zod, refus de démarrer si une variable manque), Sentry branché côté serveur et navigateur avec filtrage des données personnelles, une route de santé et une route d'erreur volontaire protégée, une CI qui vérifie chaque PR `dev` → `staging` → `main`, un test de fumée automatique sur chaque déploiement Vercel, et un guide pas à pas pour les réglages que seul le fondateur peut faire (Vercel, Sentry, secrets GitHub).

### Vocabulaire validé

- **Production** : environnement Vercel `production`, déployé à chaque fusion dans `main` (uniquement par PR du fondateur).
- **Préproduction** : branche `staging`, URL Vercel stable, variables `preview`. `dev` n'a que des déploiements de prévisualisation jetables.
- **Application vide** : page d'accueil minimale ; aucun design (U02).
- **Erreur volontaire** : déclenchée sur un environnement déployé, visible dans Sentry avec stack lisible et sans donnée personnelle.
- **Structure de dossiers** : seuls les dossiers utilisés par U01 sont créés ; les autres naissent avec leur unité.

### Décisions prises

1. **Versions** : TypeScript 6.0.3, ESLint 9.39.5, React 19.3.0. TS 7 et ESLint 10 sont incompatibles avec `typescript-eslint` (`typescript >=4.8.4 <6.1.0`) et les plugins de `eslint-config-next` (ESLint ≤ 9). → `library-docs.md` + AD-21.
2. **Git** : Claude commite et pousse uniquement sur `dev` ; le fondateur ouvre les PR vers `staging` puis `main`. → AD-22 + `code-standards.md`.
3. **Déploiement** : intégration Git native de Vercel. `main` = production ; `staging` reçoit un domaine stable.
4. **Variables d'environnement incrémentales** : `env.ts` ne valide que les variables utilisées à ce stade ; chaque unité ajoute les siennes.
5. **Variables U01** : `SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN` et `CRON_SECRET` obligatoires quand `VERCEL_ENV` vaut `preview` ou `production`, facultatives en local et en CI. `SENTRY_AUTH_TOKEN` n'existe qu'au build (source maps).
6. **Erreur volontaire** : `GET /api/health/sentry-check`, protégée par `Authorization: Bearer <CRON_SECRET>` (401 `UNAUTHENTICATED` sinon), lève une erreur si le secret est bon. Conservée pour vérifier chaque environnement.
7. **Contrôles sur les PR** : `ci.yml` conservé, plus un job qui refuse tout fichier `.env` commité ; nouveau `smoke.yml` déclenché par `deployment_status` réussi, qui appelle `/api/health` sur l'URL déployée.
8. **Scripts npm** : seuls ceux dont l'outil est installé (`test:e2e` en U04, `db:*` en U03, `eval` en U13).

### Hypothèses

- Le fondateur crée les comptes Vercel (projet relié au dépôt) et Sentry et saisit les secrets, selon `docs/setup-deploiement.md`.
- La protection des déploiements Vercel reste active ; le test de fumée passe avec `VERCEL_AUTOMATION_BYPASS_SECRET` (secret GitHub).
- Sentry : 10 % des traces en production, 100 % des erreurs, Session Replay désactivé (Q15).
- Node 24 installé sur le poste du développeur.

### Fichiers créés / modifiés

- `package.json`, `package-lock.json` — versions, `zod` 4.6.5, `server-only` 0.0.1, `@sentry/nextjs` 11.5.0 (versions exactes).
- `src/server/env.ts` (+ test) — schéma zod, règle « obligatoire sur Vercel ».
- `src/schemas/errors.ts` — codes d'erreur et statuts HTTP.
- `src/server/http/respond.ts` — réponses `{ ok, data | error }`.
- `src/app/api/health/route.ts`, `src/app/api/health/sentry-check/route.ts` — routes minces.
- `src/server/health/sentry-check.ts` (+ test) — vérification du secret en temps constant.
- `src/instrumentation.ts`, `src/instrumentation-client.ts`, `src/server/observability/sentry-scrub.ts` (+ test) — Sentry et `beforeSend`.
- `next.config.ts` — `withSentryConfig`.
- `src/app/page.tsx`, `src/app/layout.tsx` — page minimale, `lang="fr"` ; suppression des fichiers d'exemple de `public/`.
- `.github/workflows/ci.yml`, `.github/workflows/smoke.yml`.
- `docs/setup-deploiement.md` — guide Vercel, Sentry, secrets GitHub.
- `context/library-docs.md`, `code-standards.md`, `progress-tracker.md`, `architecture.md`.

### Comment le construire

1. Dépendances, puis vérifier lint / typecheck / build.
2. `errors.ts`, `respond.ts`, `env.ts` et tests.
3. Routes de santé et service, avec tests.
4. Sentry selon la doc de la version installée, filtrage compris.
5. Page d'accueil nettoyée.
6. Workflows CI et test de fumée.
7. Guide de déploiement et mise à jour des fichiers de contexte.
8. lint, typecheck, test, build en local ; commit et push sur `dev`.

### Vérification

- Local : `npm run lint`, `typecheck`, `test`, `build` passent.
- CI qui casse : une erreur de type volontaire (branche locale jetable, jamais poussée) fait échouer `npm run typecheck`.
- Après les réglages du fondateur : PR `dev` → `staging` avec CI et test de fumée verts ; `curl -H "Authorization: Bearer …" https://<staging>/api/health/sentry-check` → erreur visible dans Sentry, stack lisible, sans cookie ni en-tête ; idem après fusion dans `main`.

### Invariants concernés

- 7 : entrée et secret vérifiés avant toute action.
- 8 : routes minces, logique dans `src/server`.
- 9 : `beforeSend` retire cookies, en-têtes, corps et emails ; testé.
- Aucun secret dans le dépôt : `.env*` ignoré, job CI de contrôle.
